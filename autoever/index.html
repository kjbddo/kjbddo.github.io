Chapter01

소개 · 강점

문제를 끝까지 추적하는 해결력과, 그 해결을 구조로 굳히는 인프라 설계

제가 가장 오래 해 온 일은 AWS 인프라를 세우고 운영하는 일입니다. 2026년 7월 3계층 숙박 예약 서비스의 WAS 계층을 콘솔로 세웠고, 8월에 같은 구조를 EKS Helm 차트로 다시 세웠습니다. 8월 말부터는 네 명이 진행한 최종 프로젝트에서 컨테이너 12개짜리 의료 AI 진료 지원 시스템의 AWS 인프라를 팀과 함께 Terraform과 eksctl로 세우고, 인터넷 경로가 없는 VPC에서 구축·철거를 5차까지 반복했습니다.

워크로드를 어디에 둘지 비용·보안·가용성으로 가르는 자리, 모델과 데이터를 밖으로 내보내지 않는 구조를 세워 본 경험이 바로 쓰이는 자리라고 보고 IT Architect(AWS 구축 및 운영)를 1지망으로 택했습니다. 2지망 Platform Engineer(컨테이너 플랫폼 구축 및 운영)도 EKS 위에서 Karpenter·Helm·Argo CD를 검토해 적용하고 운영한 경험이 닿습니다.

강점 두 축

  1. 01 · 문제해결력

    증상이 익숙해 보여도 원인을 확정할 때까지 손을 떼지 않습니다

    IAM·엔드포인트·리전이 전부 맞는데 Bedrock이 403을 돌려줬을 때, 정책을 넓히는 대신 서명한 본문과 실제 전송 본문을 재현해 대조했습니다. 원인은 권한이 아니라 SigV4 payload hash 불일치였고, 권한은 2개 액션 그대로 유지했습니다.

  2. 02 · 인프라 설계

    해결한 것을 코드와 구조로 굳혀, 다시 세워도 같은 결과가 나오게 합니다

    첫 운영 구축에서 첫 동기화 6건을 고치느라 약 2시간이 걸렸습니다. 수정을 전부 Terraform과 GitOps 코드에 넣은 뒤 재구축은 대기 15분, 5차까지 smoke 10/10·terraform plan 변경 없음·첫 동기화 수정 0건이었습니다.

X-ray 분석과 처방 추천 AI를 결합한 진료 지원 시스템입니다. 컨테이너 12개(Next.js, Spring Boot, FastAPI AI 서비스, MySQL, Redis, RabbitMQ, ArangoDB 등)를 AWS EKS에 배포했고, GCP에 DR을 두는 멀티클라우드 과제였습니다.

상황 · 과제 · 행동 · 결과

  1. S상황

    환자 정보를 다루는 서비스라, 인터넷으로 나가는 경로를 NAT 없이 막아야 했습니다

    처음 설계(09-01)는 NAT 하나를 두고 LLM 호출만 태우는 구조였습니다. LLM 상류를 Amazon Bedrock으로 바꾸자 NAT가 할 일이 없어졌고, 팀은 보안을 이유로 NAT 없는 구성을 택했습니다. NAT를 빼면 이미지 풀, 파드 IAM, LLM 호출, 노드 조인이 각각 다른 AWS API를 부르고, 경로 하나가 빠지면 증상은 타임아웃뿐입니다.

  2. T과제

    필요한 경로를 전부 찾아 엔드포인트로 대체하고, 인터넷이 없는 클러스터에 배포할 수 있게 CI/CD의 경계를 다시 긋는 것

    PoC가 검증하지 않은 경로는 검증된 것이 아니라는 전제로, 이미지 풀부터 추론까지 실제로 호출해 통과시켜야 했습니다. 동시에 개발자가 클러스터를 직접 만지지 않아도 배포가 되는 구조가 필요했습니다.

  3. A행동

    PoC로 경로를 통과시키고, 숨은 의존을 코드로 지웠습니다

    09-03 NAT 라우트를 지운 PoC 클러스터에서 엔드포인트 7종(ecr.api · ecr.dkr · s3 · sts · ec2 · elb · bedrock-runtime)으로 이미지 풀 · 파드 IAM · LLM 호출 · ALB 생성 · 노드 조인 · 추론을 통과시켰습니다. 운영 환경에서는 팀원이 만든 엔드포인트 12종을 검증해 2종(logs · ec2messages)을 더했습니다.

    숨은 의존은 두 단계에서 드러났습니다. PoC에서 X-ray 추론을 직접 부르자 첫 호출에 모델 가중치를 인터넷에서 받으려다 9분 넘게 멈췼고, 운영 구축에서는 Karpenter가 리전 엔드포인트가 없는 IAM API를 불러 노드 준비가 4분 40초 늦었습니다. 가중치는 빌드 때 이미지에 굽고 없으면 즉시 실패하게, Karpenter는 인스턴스 프로파일을 Terraform으로 미리 만들어 참조하게 고쳤습니다. 자체 호스팅 Argo CD가 VPC 안에서 GitHub를 읽을 수 없는 문제는 제 제안으로 AWS 관리형 Argo CD와 CodeConnections로 전환해 풀었습니다.

  4. R결과

    구축·철거 5차, smoke 10/10, 첫 동기화 수정 0건, 최종 발표 1위

    09-07 첫 운영 구축은 첫 동기화에서 6건을 고치느라 약 2시간이 걸렸습니다. 수정을 전부 코드에 반영한 09-08 재구축은 대기 15분이었고, 09-11 5차까지 구축·철거를 반복하며 smoke 10/10 통과, terraform plan 변경 없음, 첫 동기화 수정 0건을 확인했습니다. 결정과 이유, 반영 위치는 날짜별 결정 기록으로 남겼습니다.

확정한 구조

퍼블릭 서브넷과 NAT가 없는 VPC에서 외부 요청은 CloudFront · WAF에서 VPC Origin으로 내부 ALB를 거쳐 프라이빗 EKS에 닿습니다. RDS Multi-AZ · ElastiCache · Amazon MQ · EFS는 데이터 서브넷에 두어 보안그룹 체인으로만 허용했고, AWS 서비스는 인터페이스 엔드포인트 14종과 S3 게이트웨이로, LLM은 Bedrock 엔드포인트로 호출합니다. 운영자는 인바운드 0인 Bastion에 SSM Session Manager로만 접속하고, Bastion 역할의 EKS access entry로 클러스터에 접근합니다. 파드 권한은 IRSA로 서비스어카운트별 최소 권한을 받고, 시크릿은 ExternalSecrets가 Secrets Manager에서 주입합니다.

그 밖에 한 일

  • 접근 통제. 클러스터 API는 private endpoint만 열고, Bastion 역할에 EKS access entry를 주었습니다. 파드는 IRSA로 서비스어카운트별 최소 권한을 받고, 시크릿은 ExternalSecrets가 Secrets Manager의 정해진 prefix만 읽습니다. WAF는 CloudFront에 연결했습니다.
  • 병렬 구현 통합. 같은 Terraform 모듈을 세 갈래로 구현한 뒤, 통합 브랜치와 main 사이의 충돌 16개 파일과 git이 표시하지 못한 중복 5건을 병합 커밋 하나로 풀었습니다. 채택 기준(구조는 main 기준, 출력 이름은 GitOps 저장소가 쓰는 이름으로 통일)은 PR 본문에 적었습니다. 브랜치 조사와 영역별 채택 기준 문서는 팀원의 작업입니다.
  • GCP DR(Pilot Light). 팀원과 함께 평시에는 VPC · VPN · Cloud SQL 복제만 유지하고 GKE 등 실행 환경은 DR 선언 후 만드는 구조로 준비했습니다. RDS → Cloud SQL 복제 PoC에서 변경 반영 지연 p95 0.218초를 확인했습니다.
  • 백엔드 · AI 서비스. Spring Boot API(역할 기반 접근 통제, 행 잠금, 접근 감사 로그, 테스트 270개)와 FastAPI AI 서비스를 개발했습니다. 모든 LLM 호출은 게이트웨이 한 곳을 거치고 자격증명은 그곳에 IRSA로만 둡니다. 적재 Job은 기준선 건수와 정확히 일치해야 성공하고, 부분 적재는 실패로 처리하며, 다시 돌려도 결과가 같게 만들었습니다.

Chapter03

CI/CD · 운영 자동화

클러스터에 닿는 것은 Argo CD뿐. 확인은 사람이 아니라 스크립트가 한다

저장소를 앱 · 인프라 · GitOps 셋으로 나눴습니다. 앱 CI에는 kubeconfig가 없고, 인프라 CI는 AWS OIDC만 가지며, 변경을 EKS에 반영하는 것은 AWS 관리형 Argo CD 하나입니다.

  1. 앱 저장소

    이미지 게시 + GitOps PR까지만

    CI는 이미지를 빌드해 ECR에 게시하고, GitOps 저장소에 태그 변경 PR을 올리는 데서 끝납니다. 자동 PR은 팀원이 구현했고, 저는 수명이 긴 개인 토큰이 환경 격리 없이 있는 점을 짚어 GitHub App 단기 토큰과 main 전용 environment를 제안했습니다. environment 지정으로 바뀌는 OIDC subject에 맞춰 AWS 신뢰 정책은 제가 고쳤습니다.

  2. GitOps 저장소

    Helm 차트 1개로 앱 12개, Argo CD가 읽어 반영

    app-of-apps로 앱 12개를 정의하고, AWS 관리형 Argo CD가 CodeConnections로 읽어 EKS에 반영합니다. 이미지는 CRITICAL CVE 게이트를 통과해야 배포됩니다. 베이스 이미지의 번들 CVE가 게이트를 막았을 때는 runner 스테이지에서 npm · corepack을 제거해 취약 레이어 자체를 없앴습니다.

  3. 인프라 저장소

    OIDC로 plan 검증, 2인 승인 뒤 적용

    GitHub Actions가 OIDC로 Terraform plan을 검증하고 저장된 plan을 배포합니다. 적용은 요청자가 아닌 팀원이 승인해야 진행되는 게이트를 거칩니다.

클러스터에 닿는 것은 Argo CD뿐. 앱 CI에는 kubeconfig가 없다.개발자가 클러스터를 만지지 않아도 배포가 되고, 누가 무엇을 바꿨는지 Git 이력에 남습니다.

운영 자동화 스크립트(Python)

  • 2인 승인 게이트. 인프라 적용은 실행 한 번이 요청이자 승인이어서 권한이 있으면 혼자 운영 환경을 바꿀 수 있었고, GitHub 필수 리뷰어는 유료 플랜 전용이었습니다. 팀원들과의 커피챗 논의에서 나온 안을 제가 이슈 기반 승인 스크립트(테스트 18개)로 만들었습니다. 적용을 요청하면 이슈가 열리고, 요청자가 아닌 등록된 팀원이 승인 코멘트를 달 때까지 기다립니다. 자기 승인 불가, 거부 또는 60분 초과면 중단. 사흘간 요청 10건 중 8건이 팀원 승인 뒤 진행되고 2건은 제가 취소했습니다.
  • smoke 10항목. 09-08 재구축에서 런북의 수동 curl 확인은 통과했는데 브라우저에서만 403이 났습니다. curl은 Origin 헤더를 보내지 않아 CORS 허용 목록 오류를 잡지 못한 것입니다. 확인 목록 10개를 Python smoke 스크립트로 만들며 처음부터 Origin을 붙였고, 다음 구축(09-09)에서 같은 오류를 실제로 잡아냈습니다.
  • 부트스트랩 · 동기화 대기 · 값 생성. SSM을 거쳐 Bastion으로 허용 목록의 kubectl 명령만 보내는 부트스트랩, Argo CD 동기화 대기, 새 리소스 참조를 생성해 대조하는 값 생성 스크립트를 만들었습니다. 09-19 재구축에서 팀원이 값 생성 스크립트로 새 리소스 17개 참조를 생성·대조했다고 PR 본문에 적었습니다.
  • 경보 임계값 실측 대조. 권한 거부 5분 20건, 감사 거부 5분 50건으로 둔 CloudWatch 경보 임계값을 구축 직후 실측과 대조하니 최댓값이 9건과 28건으로 한 번도 닿지 않았습니다. 표본이 10시간 남짓이라 대표성이 없다고 보고, 표본이 쌓일 때까지 재조정을 미루고 설명 문구에 뒤바뀌어 적힌 임계값만 먼저 바로잡았습니다. 고치지 않기로 한 결정에도 이유를 붙였습니다.

콘솔로 세운 Staybook의 3-tier가 재현되지 않는 점이 아쉬워 Kubernetes로 다시 세웠습니다. nginx(Web) · Spring Boot(App) · RDS MySQL(Data) 3계층 Helm 차트, Web 노드그룹 taint, App HPA 2~6, 멀티스테이지 Dockerfile.
