Chapter01

공고 요건 ↔ 경험

PUBG DevOps 팀의 필수 요건과 우대 사항에 제 경험을 하나씩 대응시키고, 공동 작업은 본인 몫을 따로 적었습니다

Chapter02

같은 장애를 두 번 겪지 않는 운영 사이클

장애 · 문제 → 원인 확정 → 코드 · 표준 · 자동화로 옮긴 것. 사람의 기억이 아니라 스크립트와 Terraform이 다음 구축을 막아 줍니다

증상이 익숙해 보여도 원인을 확정할 때까지 손을 떼지 않았고, 확정한 원인은 반드시 코드나 스크립트로 옮겼습니다. 아래 여섯 건은 PoC와 운영 구축, 중간 프로젝트에서 실제로 겪은 것이고, 날짜와 단계를 함께 적었습니다.

SLI · 경보 · 고치지 않기로 한 결정

경보는 거는 것보다 실측과 대조하는 쪽이 어려웠습니다. 고치지 않기로 한 결정에도 이유를 붙여 두어야 다음 사람이 같은 판단을 재현할 수 있습니다.

  1. 01 · Alert thresholds

    경보 임계값을 실측과 대조하고, 표본이 부족해 재조정을 보류했습니다

    권한 거부 5분 20건, 감사 거부 5분 50건으로 둔 CloudWatch 경보 임계값을 구축 직후 실측과 대조하니 최댓값이 9건과 28건으로 한 번도 닿지 않았습니다. 바로 낮추면 경보는 울리겠지만 표본이 10시간 남짓이라 대표성이 없다고 보고, 표본이 쌓일 때까지 재조정을 미루고 설명 문구에 뒤바뀌어 적힌 임계값만 먼저 바로잡았습니다. 보류한 이유는 결정 기록에 남겼습니다.

  2. 02 · Integrity SLI

    정합성 위반 7종을 5분 주기로 세어, 75시간 동안 관측된 샘플 전부에서 0건을 확인했습니다

Chapter03

운영을 Self-service에 가깝게

클러스터에 닿는 것은 Argo CD뿐. 확인 · 승인 · 값 생성은 사람이 아니라 스크립트가 하고, 동료가 그대로 씁니다

저장소를 앱 · 인프라 · GitOps 셋으로 나눴습니다. 앱 CI에는 kubeconfig가 없고, 인프라 CI는 AWS OIDC만 가지며, 변경을 EKS에 반영하는 것은 AWS 관리형 Argo CD 하나입니다. 개발자가 클러스터를 만지지 않아도 배포가 되고, 누가 무엇을 바꿨는지 Git 이력에 남습니다.

  1. App repo

    이미지 게시 + GitOps PR까지만

    CI는 이미지를 빌드해 ECR에 게시하고, GitOps 저장소에 태그 변경 PR을 올리는 데서 끝납니다. 자동 PR은 팀원이 구현했고, 저는 수명이 긴 개인 토큰이 환경 격리 없이 있는 점을 짚어 GitHub App 단기 토큰과 main 전용 environment를 제안했습니다.

  2. GitOps repo

    Helm 차트 1개로 앱 12개, Argo CD가 읽어 반영

    app-of-apps로 앱 12개를 정의하고, AWS 관리형 Argo CD가 CodeConnections로 읽어 EKS에 반영합니다. 이미지는 CRITICAL CVE 게이트를 통과해야 배포됩니다.

  3. Infra repo

    OIDC로 plan 검증, 2인 승인 뒤 적용

    GitHub Actions가 OIDC로 Terraform plan을 검증하고 저장된 plan을 배포합니다. 적용은 요청자가 아닌 팀원이 승인해야 진행되는 게이트를 거칩니다.

클러스터에 닿는 것은 Argo CD뿐. 앱 CI에는 kubeconfig가 없다.클러스터 API는 private endpoint만 열고, 운영자는 인바운드 0인 Bastion에 SSM Session Manager로만 접속합니다.

동료가 그대로 쓰는 도구 · 표준

  • 2인 승인 게이트(Python, 테스트 18개). 인프라 적용은 실행 한 번이 요청이자 승인이어서 권한이 있으면 혼자 운영 환경을 바꿀 수 있었고, GitHub 필수 리뷰어는 유료 플랜 전용이었습니다. 팀원들과의 커피챗 논의에서 나온 안을 제가 이슈 기반 승인 스크립트로 만들었습니다. 적용을 요청하면 이슈가 열리고, 요청자가 아닌 등록된 팀원이 승인 코멘트를 달 때까지 기다립니다. 자기 승인 불가, 거부 또는 60분 초과면 중단. 사흘간 요청 10건 중 8건이 팀원 승인 뒤 진행되고 2건은 제가 취소했습니다.
  • smoke 10항목. 구축한 사람이 누구든 같은 확인을 하도록 확인 목록 10개를 Python 스크립트로 고정했습니다. Origin 헤더를 붙여 CORS까지 검사하고, 5차 구축까지 10/10이었습니다.
  • 부트스트랩 · 동기화 대기 · 값 생성. SSM을 거쳐 Bastion으로 허용 목록의 kubectl 명령만 보내는 부트스트랩, Argo CD 동기화 대기, 새 리소스 참조를 생성해 대조하는 값 생성 스크립트를 만들었습니다. 09-19 재구축에서 팀원이 값 생성 스크립트로 새 리소스 17개 참조를 생성·대조했다고 PR 본문에 적었습니다.
  • 런북 · 결정 기록. 구축 순서 런북과, 결정 · 이유 · 반영 위치를 날짜별로 남긴 decision.md를 유지했습니다. 바꾸지 않기로 한 것(경보 임계값 보류)도 이유와 함께 적어 동료가 같은 판단을 재현할 수 있게 했습니다.
  • CVE 게이트. 이미지는 CRITICAL CVE 게이트를 통과해야 배포됩니다. 베이스 이미지의 번들 CVE가 게이트를 막았을 때는 예외를 두는 대신 runner 스테이지에서 npm · corepack을 제거해 취약 레이어 자체를 없앴습니다.
  • ECR 미러 갱신 정책. 노드가 public ECR · ghcr · Docker Hub에 닿지 못해 공개 이미지와 Helm 차트를 ECR로 미러했습니다. 미러 과정에서 다이제스트가 바뀌어 ImagePullBackOff가 나자 태그로만 당기게 고쳤고, 자동 패치가 안 되므로 월 1회와 보안 공지 때 갱신, CI에서 버전 대조, ECR 지속 스캔을 정책으로 두었습니다.

동료와 함께 고친 것

팀원이 이미지 게시 뒤 GitOps 저장소에 태그 변경 PR을 자동으로 여는 CI를 올렸을 때, 방향(변경은 자동 PR, 병합은 사람)은 맞다고 먼저 적고 막을 이유 3건을 냈습니다. 수명이 긴 개인 토큰이 환경 격리 없이 저장소 시크릿에 있는 것, 앞선 실행이 영구 실패하면 이후 main push가 모두 막히는 것, 사람이 PR 표식을 지우면 이후 제안이 교착하는 것입니다. 대안으로 GitHub App 단기 토큰과 main 한정 environment를 제시했고, 개인 토큰을 유지하더라도 환경 격리는 필수라는 최소 조건도 적었습니다. 단기 토큰 전환의 구현은 팀원의 작업입니다.

재리뷰에서는 environment를 지정하면 AWS가 보는 신원 값(OIDC subject)이 바뀌어 역할 신뢰 정책에서 거부될 것을 파일 · 행 단위로 짚었고, 신뢰 정책에 subject 2종을 추가하는 수정은 제가 직접 올렸습니다. 팀원도 제가 놓친 2건(런북 예시의 subject 수, 재구축 첫 실행 때 이미지 8개 전부 게시)을 짚어 주었고, 저는 팀원이 제안한 구조대로 가드 테스트 3개를 올렸습니다. 로그에서 환자 식별자를 빼는 작업에서도 제가 앱 로그를 고치고 팀원이 수집기 필터를 넣은 뒤, 오류 번호 · 작업 ID · 코드 위치까지 사라진 문제를 팀원이 제기해 구조화 진단 객체로 절충했습니다.

WAS를 t2.nano → t3.nano → t3.small로 바꿔 가며 8회 이상 구축하고 k6 · CloudWatch · Grafana로 측정했습니다. t3.nano는 초당 50건에서 메모리 90%대, t3.small은 초당 150건에서 50%대였습니다. 사양을 더 올리는 대신 t3.small 2대로 시작해 CPU 60% 목표 추적으로 최대 6대까지 늘리기로 했고, 워밍업 300초는 콜드스타트 실측으로 정했습니다. 계정 이전으로 전부 0.0.0.0/0이 된 보안그룹은 참조 체인(CloudFront prefix-list → ALB → WAS 8080 → DB 3306 · 캐시 6379)으로 복원했고, Tomcat 로그는 인스턴스 종료 시 소실되지 않도록 CloudWatch Logs로 수집했습니다.

Spring PetClinic 3-tier on EKS: Helm 차트와 계층 격리

콘솔로 세운 Staybook의 3-tier가 재현되지 않는 점이 아쉬워 Kubernetes로 다시 세웠습니다. nginx(Web) · Spring Boot(App) · RDS MySQL(Data) 3계층 Helm 차트, Web 노드그룹 taint, App HPA 2~6, 멀티스테이지 Dockerfile.

NetworkPolicy만으로는 "Web → App만 허용"이 안 됐습니다. ALB → Web 트래픽은 파드 라벨이 없는 외부 IP에서 오고, App → RDS는 클러스터 밖이라 셀렉터로 잡히지 않습니다. 그래서 경계마다 두 겹을 겹쳤습니다. Internet ↔ Web은 ALB 보안그룹 + ipBlock 정책, Web ↔ App은 라벨 정책 + 노드그룹 · 서브넷 분리, App ↔ Data는 egress 정책 + RDS 보안그룹 체이닝.
