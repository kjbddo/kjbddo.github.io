Chapter01

소개

왜 이 일을, 왜 교보문고인가

컴퓨터공학을 전공하며 서비스를 만들었지만, 로컬에서 돌아가는 코드를 사용자에게 닿게 하는 단계에서 막혔습니다. 코드만으로는 서비스가 완성되지 않는다는 것을 느껴 멀티클라우드 엔지니어링 과정 1,000시간을 선택했습니다.

교보문고는 송도 데이터센터와 AWS를 함께 운영하며 컨테이너와 DevOps 적용 범위를 넓혀 왔고, 비용을 예측 가능하게 하려고 클라우드에 있던 데이터 웨어하우스를 온프레미스로 옮기기도 했습니다. 클라우드를 정답으로 두지 않고 워크로드마다 무엇을 어디에 둘지 따지는 방식이라고 이해했습니다.

저는 같은 고민을 프로젝트에서 직접 계산하며 배웠습니다. NAT를 지우면 비용이 줄어든다고 가정했지만, VPC 엔드포인트는 가용 영역마다 과금되어 월 약 414달러가 나왔습니다. 팀은 보안을 이유로 그 비용을 감수하기로 결정하고, 이유와 함께 기록했습니다.

핵심 강점

  1. 1

    닫힌 네트워크에서 필요한 경로를 전부 찾는다

    폐쇄망 전환에서 숨은 외부 의존 4건을 찾아 제거했습니다.

  2. 2

    개발자가 클러스터를 만지지 않는 배포

    앱 CI에 kubeconfig를 두지 않는 3저장소 권한 모델과 Argo CD GitOps로 배포 체계를 세웠습니다.

  3. 3

    지표와 기록으로 말한다

    부하 테스트로 사양을 정했고, 결정과 이유를 날짜별로 남겼습니다.

폐쇄망 구조

VPC에는 NAT도, Public 서브넷도, 기본 경로도 없습니다. 사용자 트래픽은 CloudFront와 WAF를 거쳐 VPC origin으로 내부 ALB에 닿고, 운영자는 Bastion과 SSM Session Manager로만 접근합니다.

3저장소 배포 흐름

저장소를 앱 · 인프라 · GitOps 셋으로 나눴습니다. 앱 저장소의 CI는 이미지를 ECR에 게시하고 GitOps 저장소에 PR을 올리는 데서 끝납니다. 변경을 EKS에 반영하는 것은 AWS 관리형 Argo CD뿐입니다.

한 일

  • Terraform 모듈 8개(network · vpc-endpoints · security · data · platform · karpenter · argocd · app)로 인프라를 구성하고 state는 환경당 하나로 두었습니다. 일부 모듈은 팀원이 병렬로 구현했고, 36개 파일에서 난 충돌을 PR 하나에서 해결해 통합했습니다.
  • 접근 통제. 클러스터 API는 private endpoint만 열고, Bastion 역할에 EKS access entry를 주었습니다. 파드는 IRSA로 서비스어카운트별 최소 권한을 받고, 시크릿은 ExternalSecrets가 Secrets Manager에서 주입합니다. WAF는 CloudFront에 연결했습니다.
  • 코드 리뷰. 팀원의 CI PR이 장기 토큰을 쓰는 점을 짚어 OIDC로 전환했습니다.
  • Python 운영 자동화. SSM을 거쳐 Bastion으로 허용 목록의 kubectl 명령만 보내는 부트스트랩 · 동기화 대기 · smoke 테스트(10개 항목) 스크립트를 만들었습니다.

어려움 4건

1문제

첫 추론이 9분 넘게 응답 없음

원인

추론 서비스가 첫 호출 때 모델 가중치를 인터넷에서 받는데 타임아웃이 없었습니다. PoC에서는 초기 데이터를 적재하는 Job이 NAT를 지우기 전에 실행되어 이 문제가 드러나지 않았습니다.

해결

모델 가중치를 빌드 때 이미지에 포함하고, 가중치가 없으면 가짜 결과로 넘어가지 않고 즉시 오류로 실패하게 했습니다. CI에는 사전 다운로드 단계를 넣었습니다.

2문제

Argo CD가 GitHub를 읽지 못함

원인

GitHub에는 VPC 엔드포인트가 없습니다. PoC는 kubectl apply로 직접 배포해 검증했기 때문에, Argo CD가 GitHub를 읽는 경로는 확인하지 못했습니다.

해결

AWS 관리형 Argo CD와 CodeConnections로 전환했습니다. 동기화 타임아웃이 120초로 고정이라, 수 분 걸리는 적재 작업은 동기화 훅에서 빼 일반 Job으로 바꿨습니다.

3문제

컨트롤러가 부르는 글로벌 API에 닿지 못함

원인

Karpenter가 호출하는 IAM · Pricing은 서울 리전에 엔드포인트가 없습니다. isolatedVPC 설정이 빠져 있어 30초 타임아웃이 반복됐고, 노드 클래스 준비가 4분 40초 늦어졌습니다(실측).

해결

설정을 추가하고 인스턴스 프로파일은 Terraform으로 미리 생성했습니다. 로드밸런서 컨트롤러의 WAF · Shield 호출도 같은 이유로 비활성화했습니다.

4문제

공개 레지스트리 접근 불가

원인

폐쇄망에서는 공개 레지스트리에 닿을 수 없어 이미지와 Helm 차트를 ECR로 미러했는데, 미러 과정에서 다이제스트가 바뀌어 ImagePullBackOff가 났습니다.

해결

이미지를 태그로만 당기게 수정했습니다. 미러는 자동 패치가 안 되므로 월 1회, 그리고 보안 공지가 나올 때마다 갱신하고 CI에서 버전을 대조합니다.

새로 배운 것

  • 인터페이스 엔드포인트와 게이트웨이 엔드포인트는 다르고, private DNS가 어떻게 동작하는지 알아야 한다.
  • 엔드포인트 경로와 IAM 권한은 별개다.
  • IAM · Pricing처럼 리전 엔드포인트가 없는 글로벌 서비스가 있다.
  • 엔드포인트는 가용 영역별 ENI당 과금된다. 14종 × 3AZ = ENI 42개, 월 약 414달러. "NAT 제거 = 절감"이라는 가정은 틀렸고, 팀은 보안을 이유로 이 비용을 감수하기로 결정하고 기록했다.
  • curl 검증은 브라우저 동작을 보장하지 않는다.
  • PoC가 검증하지 않은 경로는 검증된 것이 아니다.

대표 문제

문제

Tomcat이 약 10초마다 재시작

멘토 피드백에 따라 앱이 설치된 /opt를 별도 EBS로 분리하자 생긴 문제였고, 같은 방법으로 세 번 다시 시도해도 실패했습니다. 재시작을 반복하는 인스턴스에는 SSM으로도 접속할 수 없어 로그를 볼 수 없었습니다.

원인

Auto Scaling Group 밖 격리 인스턴스에서 재현했습니다.

① 서비스 유닛에 RequiresMountsFor가 없어 /opt 마운트 전에 기동
② 부팅 중 user-data의 mkfs · 복사와 경합

재시작 주기 10초가 RestartSec=10과 일치해 원인을 확정했습니다.

해결

앱 볼륨을 AMI 스냅샷에서 복원하게 바꾸고, systemd 드롭인으로 마운트 의존성을 추가했습니다. 재부팅으로 검증한 뒤 자동 롤백을 건 instance refresh로 무중단 교체했습니다(2026-07-12).

결과

루트 · 로그 · 앱 볼륨 3개로 분리하고 전부 암호화했습니다. 재시작 0회.

그 외

  • Launch Template 새 버전을 만들어도 반영되지 않던 문제 — Auto Scaling Group이 특정 버전에 고정되어 있었습니다.
  • 프로젝트 중 AWS 계정 이전으로 전부 0.0.0.0/0이 된 보안그룹을 참조 체인(CloudFront prefix-list → ALB → WAS 8080 → DB 3306 · 캐시 6379)으로 복원했습니다.
  • 인스턴스가 종료돼도 로그가 사라지지 않도록 Tomcat 로그를 CloudWatch Logs로 수집하고, logrotate를 적용했습니다.
  • EBS 기본 암호화를 켰습니다.
