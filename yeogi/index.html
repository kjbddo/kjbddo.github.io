02

숙소 예약 도메인을 직접 만들었습니다

예제 애플리케이션으로는 부하 시험의 근거가 서지 않는다고 판단해, 숙소 예약 서비스를 새로 만들자고 팀을 설득한 데서 시작한 프로젝트입니다.

설득의 근거는 기능마다 부하가 닿는 자원이 다르다는 것이었습니다. 이렇게 나뉘어야 어떤 API가 어떤 자원을 밀어붙이는지 측정으로 드러나고, 인스턴스 타입 결정에 근거가 생깁니다.
예약 충돌을 어떻게 볼 것인가:동시 예약 충돌은 409로 반환하고, 이를 장애가 아닌 정상 동작으로 정의했습니다. 미로그인(401)도 마찬가지입니다. 판정 기준을 세울 때 이 둘을 에러율에서 제외한 것이 측정의 출발점이었습니다.
판정 기준을 먼저:p95 < 500ms · 에러율 < 1%를 break 판정 기준으로 세우고 시험을 시작했습니다. 무엇을 실패로 볼지 정하지 않은 부하 시험은 숫자만 남습니다.
결론:세 가지 인스턴스 타입을 단계 부하로 비교한 결과, 스펙을 올리기보다 오토스케일링으로 분산하는 편이 낫다는 결론에 이르렀습니다. 팀은 감이 아니라 측정값으로 구조를 확정했습니다.
제가 직접 한 것:서비스 설계 제안, 예약 도메인 API 일부 구현, 진입점 보안과 관측 전 구간. 나머지 애플리케이션 코드는 팀원이 맡았습니다.
03

규격이 다른 소스를 하나의 파이프라인으로

Overlay-GPT에서 MS PowerPoint·Excel·Word·한글 네 종류의 문서를 한 파이프라인으로 다뤄야 했습니다. 대상이 문서였을 뿐, 공급사마다 인터페이스가 다른 채널연동과 같은 형태의 문제라고 생각합니다.

문제:포맷마다 마크업 문법과 구조, 이미지 처리 방식이 달라 단일 파싱 로직이 일반화되지 않았습니다. 같은 파서를 태우면 형식이 어긋났고, 이미지로 삽입된 텍스트는 파싱 자체가 불가능했습니다.
어댑터 분리:포맷별 파서를 모듈로 분리해 공통 인터페이스 뒤에 두고, PPT는 태그를 하드코딩해 구조를 명시적으로 매핑했습니다.
폴백:파싱이 불가능한 구간에는 OCR 호출을 폴백으로 두어 텍스트를 추출한 뒤 파이프라인에 합류시켰습니다.
오케스트레이션:어떤 처리를 부를지를 상황에 따라 선택하도록 에이전트의 tool calling으로 조립했습니다. LLM을 답변 생성기가 아니라 툴을 부리는 실행 주체로 설계하면 이기종 입력을 유연하게 다룰 수 있다는 것을 확인했습니다.

종료 신호가 엔드포인트 제거보다 앞섰다:파드가 서비스 목록에서 빠지기 전에 종료를 시작해, 이미 사라진 대상으로 트래픽이 잠시 흘렀습니다. 종료 전 대기와 유예 시간을 적용하자 재시험은 전량 정상이었습니다.
반대 방향의 경합도 있었다:새 파드가 준비 완료로 판정됐는데 로드밸런서 등록이 끝나지 않아 실패한 70건은, 등록 완료를 준비 조건으로 걸어 해소했습니다.
장애를 직접 주입해 복구를 확인:Terraform으로 코드화한 고가용성 구성에서 인스턴스를 강제 종료하며 2초 간격으로 요청을 보내, 150회 중 144회 정상(502 1회)·대체 인스턴스 정상 판정까지 76초를 확인했습니다. 유일한 502의 원인은 상태 확인 주기(15초 × 2회)로 설명됩니다.
